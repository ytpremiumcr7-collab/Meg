# PRR de Megalodon — revisión de la rama avanzada

Base examinada: `c9324b909c1fa0e885d6139fc1b1baafdaccd6b8`.
Rama: `fix/prr-regressions-2026-10-07`; PR #6 permanece draft.
Megalodon prepara propuestas del licitante; no publica convocatorias ni sustituye al portal de la autoridad.

## Evidencia inicial

El run GitHub Actions 37715749316 (143) terminó con los ocho jobs exitosos:
migration-recovery, python-audit, backend-integration api/core/procurement,
frontend-audit, bim-browser-acceptance y sast. Esto acredita esos jobs en esa
revisión, no todas las propiedades de operación en producción.

Se leyó el Markdown de propuestas adjunto. Se priorizan transacciones de cada
dominio, evidencia de entrada, intentos con fencing y recuperación. No se crea
un coordinador de negocio común para BIM, OCR, Procurement y Monte Carlo.

## Defectos reproducidos y primera corrección

- **P1 / sesiones ORM antiguas:** SELECT FOR UPDATE bloquea la fila pero no
  sustituye automáticamente sus atributos si ya existe en el identity map.
  Con expire_on_commit=False, Monte Carlo aceptaba completar una simulación
  cancelada por otra sesión y OCR aceptaba completar el intento antiguo después
  de un nuevo claim en otra sesión. Ambas regresiones fallaron antes del cambio.
  Los locks ahora recargan los atributos mediante populate_existing=True.
- **Atomicidad Monte Carlo:** la implementación de completar ya tenía un único
  commit para resultado y proyección presupuestaria. La regresión anterior de
  factor_impuesto inválido fallaba por autoflush antes de asignar ambos resultados.
  Se añadió un trigger de DB que rechaza específicamente UPDATE de la proyección;
  una sesión nueva verifica que ni resultado ni presupuesto quedaron persistidos.
  SQLite: 26 pruebas aprobadas (intentos, PRR y OCR durable).

## Hallazgos por código que aún requieren cierre

- **P1 / Procurement:** no hay token/lease de intento; las escrituras de negocio
  realizan commits antes del resultado del job y el worker antiguo puede finalizar
  sin comprobar quién conserva el intento. Requiere una transacción local al dominio.
- **P1 / mensajes QUEUED perdidos:** OCR y Procurement recuperan RUNNING vencidos
  y PENDING, pero no QUEUED que nunca llegan a reclamar. Monte Carlo sí los recupera.
- **P1 / presupuesto aprobado:** OCR agrega partidas de precio cero sin comprobar
  el estado del presupuesto bajo el lock de escritura.
- **P1 / compensación Storage OCR:** crear confirma la fila y después refresh;
  si falla ese refresh, la API borra la fuente aunque haya un job durable.
- **P1 / event loops:** workers usan asyncio.run repetidamente con el engine asyncpg
  global con pool; puede reutilizar conexiones ligadas a un loop cerrado. SQLite con
  NullPool no certifica este comportamiento en PostgreSQL.

Estos últimos son diagnósticos de código, no reproducciones cerradas todavía.

## Segunda corrección: OCR

Las regresiones de QUEUED perdido, intento vencido sin reclamar y aprobación del
presupuesto en otra sesión fallaron antes de la corrección. Se recuperan mensajes
QUEUED antiguos con identidad durable y sin incrementar attempts por publicación;
se rechazan token o plazo vencidos; la escritura recarga y bloquea el presupuesto,
rechaza VALIDADO/APROBADO y vuelve a BORRADOR cuando agrega partidas sin precio.
Completar hace rollback en errores para dejar la sesión reutilizable.

Crear ya no realiza un refresh falible después de confirmar el job. En una falla
ambigua, la API sólo compensa la fuente si la DB confirma que no hay job; conserva
el objeto si no puede saberlo. Se probaron errores antes y después del commit
contra la DB local, con Storage sustituido en su frontera (no acredita Supabase
real). Resultado: 13 pruebas SQLite aprobadas en intentos/OCR durable.

## Tercera corrección: Procurement y conexiones de workers

Reproducciones iniciales: commits internos sobreviven a fallo del job; el mensaje
puede ejecutar otro tender del mismo cliente; QUEUED perdido nunca se recupera.
Se añade token UUID, número de intento y lease en una migración lineal del dominio.
El worker valida usuario/tenant/tender persistidos y el hash de la revisión de
entrada, y rechaza entradas cambiadas en vez de procesar otra revisión bajo la
misma identidad.

Una conexión externa posee la transacción de negocio. Sus sesiones usan
join_transaction_mode=rollback_only: los commits de los helpers hacen flush,
pero no confirman la conexión externa. El lock NO KEY UPDATE del job permanece
hasta confirmar su resultado y todo el negocio; permite FK KEY SHARE de las
trazas independientes. Un proceso muerto revierte ese negocio y deja el claim
durable para recuperar al vencer. Se comprueba el plazo de nuevo antes del cierre.

La marca final de readiness de la traza también pertenece a esa transacción;
las etapas anteriores permanecen como diagnóstico durable provisional. Se probó
con un trigger que rechaza SUCCEEDED después de los commits internos: presupuesto
canónico y readiness revierten junto con el resultado. Los intentos antiguos no
pueden escribir el fracaso de uno nuevo. Los mensajes QUEUED vencidos se republican.

Los artefactos compilados incluyen hash de contenido en la ruta: un intento
revertido puede dejar un objeto recuperable sin sobrescribir otro contenido.
Se reprodujo y corrigió el reintento de un storage intent ERROR que chocaba contra
su propia restricción única. Se mantiene una sola identidad por ruta/hash.

Monte Carlo, OCR y Procurement y sus reconciliadores usan conexiones NullPool
para no reutilizar conexiones asyncpg entre loops cerrados. Las sesiones
independientes de trazas/storage reciben esa misma fábrica del worker. La API
conserva su pool. Se alinea el ORM de Procurement.started_at/finished_at con el
TIMESTAMPTZ de la migración original; el backfill usa ese esquema autoritativo.

**Despliegue:** detener consumo y drenar workers antiguos, aplicar alembic upgrade
head, verificar esquema y arrancar workers nuevos. No mezclar workers viejos sin
fencing con los nuevos. Esta ronda no autoriza ni ejecuta un despliegue.

Validación SQLite de los cuatro archivos de regresión: 38 aprobadas, 1 omitida
(requiere locks PostgreSQL). Se añaden además ejecución real del task Monte Carlo
con Redis en loops separados y exclusión SKIP LOCKED con dos conexiones para CI
PostgreSQL; no se declaran aprobadas hasta observar el resultado.

Las trazas de preparación del worker se vinculan por correlación al token del
intento. Un fracaso o recuperación marca la traza RUNNING de ese intento como
FAILED en la misma transacción que el job, sin tocar trazas de otros intentos.

Se encontró además **P1 reproducido de instalación Supabase**: el lockfile fijaba
websockets 12, pero Realtime 2.31 importa websockets.asyncio.client, ausente en esa
versión. La prueba instanciando los clientes reales falló por ModuleNotFoundError.
Se actualiza exclusivamente websockets a 15.0.1, compatible con el rango <16 de
Realtime, y se conservan las demás versiones del lockfile. Los clientes HTTP del
worker se crean por scope de loop y se cierran; no reutilizan el singleton de API.
La prueba no hace llamadas a Supabase remoto y no certifica aislamiento remoto.

Referencias técnicas contrastadas con el código instalado:
- https://docs.sqlalchemy.org/en/20/orm/session_api.html (rollback_only)
- https://websockets.readthedocs.io/en/15.0.1/ (API asyncio desde v13)
